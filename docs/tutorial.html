Tutorial do dev-harness

Da instalação à release: como usar o kit no dia a dia, o que ele grava em .harness/ e o que cada comando faz.

data 2026-09-30 status interno path docs/tutorial.html

01Instalação

Pré-requisitos: Git e Claude Code autenticado, com acesso a um modelo. O pacote traz o binário dh; não precisa de interpretador. Go 1.22+ só para quem mantém o kit.

  1. Pelo marketplace. Dentro de uma sessão do Claude Code, no projeto em que você vai trabalhar. A forma por URL baixa só o marketplace.json, sem clonar o repositório: 
    /plugin marketplace add https://raw.githubusercontent.com/danielmalka/dev-harness/main/.claude-plugin/marketplace.json
/plugin install dh@dev-harness
    A forma curta /plugin marketplace add danielmalka/dev-harness também funciona, mas clona o repositório inteiro (cerca de 90 MB, por causa dos binários dh de cada versão) e já falhou uma vez com fetch-pack: invalid index-pack output (não reproduzido). Com um clone local, /plugin marketplace add /caminho/do/clone serve também. Em todas as formas o install baixa só a pasta do plugin, na tag fixada em .claude-plugin/marketplace.json, de onde vem a versão. Para um time, o projeto pode declarar o marketplace em extraKnownMarketplaces e o plugin em enabledPlugins no .claude/settings.json.
  2. Ou a partir do clone (desenvolvimento). Clone o repositório e carregue o pacote gerado, no projeto alvo: 
    claude --plugin-dir "/caminho/absoluto/do/clone/dist/claude-code/dev-harness" --agent coordinator
    Dentro de aspas o ~ não expande: "~/projetos/..." não existe, o Claude ignora o plugin em silêncio e --agent coordinator falha com "not found". Use $HOME/... ou o caminho completo. Se o runtime exigir o nome qualificado, use --agent dh:coordinator.
  3. Migrando de antes da 0.8.0. /plugin uninstall dev-harness@dev-harness, depois /plugin install dh@dev-harness; troque /dev-harness: por /dh: em scripts e anotações próprias.
  4. Desativar. Encerre a sessão sem o --plugin-dir ou desinstale o plugin. Os arquivos em .harness/ do projeto ficam: o kit não apaga trabalho seu.

O pacote inclui settings.json e hooks/hooks.json, que gravam snapshots por sessão em ~/.harness/sessions/<session_id>.json (a pasta global, ver Modo global), só em arquivos locais e podados após 7 dias.

02Dashboard local

Uma página local mostra projetos em andamento, PRDs abertos, e sessões do Claude Code com seu estado (trabalhando, parado, esperando você, erro, pronto ou atenção). Rodar:

  1. /dashboard dentro de uma sessão do Claude Code. O comando (registrado pelo mod, não é um /dh: tradicional) sobe um servidor na porta padrão 4747 em http://127.0.0.1:4747 e imprime a URL. Aceita argumentos:
    • --port N para mudar a porta (ex: /dashboard --port 4748). Se a porta estiver ocupada, o comando avisa com clareza.
    • --detach para desacoplar; por padrão o servidor roda enquanto a sessão ativa.
    • --stale D e --done-decay D para tuning de exibição (padrões sensatos vêm pré-configurados).
  2. Projetos. O dashboard lista os projetos registrados em ~/.harness/config.yaml, em modo repo ou global. Registre cada um com /dh:setup ou dh link dentro do repositório; o arquivo é relido a cada atualização, sem reiniciar. Projeto de antes da 0.21.0 só aparece depois de dh link. A lista sem servidor sai de dh projects --json.
  3. Avatares customizados (opcional). A chave dashboard.sprites do config.yaml aponta para uma pasta de ícones no formato jevmon: um arquivo por pose (<pose>.png ou frames <pose>_01.png, <pose>_02.png, etc.), mais um poses.json opcional que mapeia estados. O kit envia 6 ícones exemplo (parado, trabalhando, esperando, erro, pronto, atenção). Quando uma pose não existe na sua pasta, o dashboard cai na padrão do kit. O servidor nunca serve ícone com caminho livre (sem nome de pose conhecido) por segurança.
  4. Parar o dashboard. dh dashboard --stop pede ao dashboard da porta padrão que saia; use --port N para outra porta. Não mata processo: se a porta estiver ocupada por outro programa, o comando sai com erro e o motivo. Não combina com --detach. Dashboard anterior à 0.20.0 não tem essa rota: pare-o manualmente uma vez. 
    dh dashboard --stop --port 4748
  5. Conferir a configuração em uso. /api/state traz o campo config com {home, sprites, port} (a pasta global, a pasta de sprites e a porta); cada item de projects[] traz name, path, mode (repo ou global) e harness (a pasta resolvida). A extensão VS Code usa esses campos.
  6. Token de parada. Ao subir, o dashboard grava um token aleatório em ~/.harness/dashboard/stop-<porta>.token (a pasta global; DH_HOME muda o lugar). A pasta é 0700 e o arquivo 0600; no Windows, quem protege é o ACL do perfil do usuário. O arquivo fica no disco depois de sair, de propósito: um token antigo não serve, porque a próxima subida o sobrescreve. Nenhuma página web ou iframe para o dashboard: requisições com cabeçalho Origin são recusadas. As pastas antigas ~/.claude/dev-harness/sessions e <pasta de configuração do usuário>/dev-harness/dashboard ficam órfãs na 0.21.0 e podem ser apagadas. Um dashboard anterior à 0.21.0 ainda em execução tem de ser parado à mão uma vez (ele não conhece o token novo).

03Extensão VS Code

A extensão dev-harness-vscode traz o dashboard local para dentro do VS Code, mostra o estado das sessões na barra de status e abre um terminal para rodar um comando do dh sem sair do editor.

  1. Instalar a extensão. Baixe dev-harness-<versão>.vsix do release mais recente do repositório danielmalka/dev-harness-vscode. No VS Code, abra a paleta de comandos (Ctrl+Shift+P / Cmd+Shift+P), procure "Extensions: Install from VSIX..." e escolha o arquivo.
  2. Configurar o dashboard. Configurações opcionais em Configurações (Ctrl+,) do VS Code:
    • dh.dashboard.port: porta do servidor (padrão 4747).
    • dh.dashboard.roots e dh.dashboard.sprites: deixam de valer na 0.21.0 (os projetos e os sprites vêm do config.yaml); saem na próxima versão da extensão.
  3. Abrir o dashboard. Na barra de atividades (esquerda), clique no ícone "Dev Harness" para abrir a view. Se o servidor não está rodando, clique em "Iniciar dashboard" para subi-lo desacoplado. O dashboard carrega em um iframe.
  4. Abrir uma sessão. Abra a paleta de comandos e procure por "dh: abrir sessão". Escolha a pasta do projeto (subpastas sob as raízes, ou pastas abertas no workspace) e um comando /dh:<nome> da lista dos 19 (ex: /dh:auto ou /dh:improve). Um terminal integrado abrirá naquela pasta, rodará claude e digitará o comando — você pressiona Enter para enviar.

04Primeira sessão

Abra o Claude Code no projeto, com o Coordenador como agente principal (--agent coordinator quando carrega do clone), e rode:

  1. /dh:doctor diagnostica kit, runtime e projeto. Não escreve nada. Sem o Claude, no clone: dist/claude-code/dev-harness/bin/dh doctor dist/claude-code/dev-harness.
  2. /dh:setup lê o projeto (pilha, manifestos, comandos de teste, lint e build) e propõe o perfil. Com autorização para escrever, grava .harness/project.yaml e, só se ainda não existirem, MEMORY.md, EPOCHAL.md e RISKS.md. O campo language (en por padrão, pt-br se você escreveu em português) escolhe templates/<lang>/. Um AGENTS.md do projeto é canônico; um CLAUDE.md também é lido, e em conflito vale o AGENTS.md.
  3. Treino opcional. A fixture evals/fixtures/slice-01 (clone do kit; Python 3, unittest, um critério vermelho de propósito) serve para um primeiro ciclo plan, build, verify, review, handoff. Não copie expected/greet.py no lugar do código.

05O que vive em .harness/

CaminhoPara que serve
project.yamlPerfil do projeto: language, commands, reviewers. Ver Configuração.
local.yamlCaminhos e slugs de CLIs desta máquina. Sem segredos.
MEMORY.mdEstado ativo: trabalho atual, decisões, bloqueios, próximo passo.
EPOCHAL.mdArquivo dos lotes de memória, escrito por /dh:consolidate-memory. Só se lê para uma pergunta histórica concreta.

Só o Coordenador escreve MEMORY.md, EPOCHAL.md e RISKS.md. Os outros agentes devolvem propostas. O plugin Claude Code força essa regra em tempo de execução: um subagente que tenta escrever naqueles arquivos é bloqueado. O disco é a verdade: se você apagou registros, o Coordenador não os recria de memória da conversa.

05bModo global

Para quem não pode deixar pasta do dh na árvore do repositório (por exemplo, colegas que não usam o dh), o estado do projeto vive em uma pasta global por máquina e por ambiente, ~/.harness/ (DH_HOME muda o lugar; no Windows, %USERPROFILE%\.harness). O dh a cria no primeiro uso:

~/.harness/
  config.yaml        # padrões (language, reviewers, mode, dashboard.sprites) e o mapa projects:
  projects/<nome>/   # MEMORY, EPOCHAL, RISKS, project.yaml, local.yaml, tasks/, prd/ (direto, sem subpasta)
  sessions/          # snapshots de todas as sessões
  dashboard/         # token de parada do dashboard

Todo projeto fica registrado em projects: (caminho do repositório para nome, o nome da pasta do repositório), com .harness/ interno ou global. Só o dh escreve o config.yaml; mods e scripts perguntam a dh harness-path. A resolução é única: <repo>/.harness/ se existir (modo repo, vence sempre); senão ~/.harness/projects/<nome>/ pelo mapa (modo global); senão none, e o /dh:setup oferece criar. A sessão recebe o modo e a pasta resolvidos ao abrir. A trava que impede subagentes de escrever MEMORY.md, EPOCHAL.md e RISKS.md vale nos dois lugares.

  1. Instalar no trabalho. Instale o plugin como na seção Instalação. Cada ambiente (WSL, Windows, macOS) tem a sua pasta global; o kit não traduz caminhos entre eles.
  2. Permitir a pasta global. Você mesmo adiciona ~/.harness em additionalDirectories no ~/.claude/settings.json, para o Claude Code poder escrever lá. O /dh:doctor só sugere a entrada; nunca grava. 
    { "permissions": { "additionalDirectories": ["~/.harness"] } }
  3. Rodar o setup. /dh:setup pergunta uma vez, para o projeto, se o modo é repo ou global (ou usa mode do config.yaml), copia language e reviewers do config.yaml para o project.yaml novo e registra o projeto. Em global nada é escrito na árvore: sem pasta, sem arquivo, sem linha de .gitignore. O .harness/ interno é versionado; só o local.yaml deve ficar ignorado.
  4. Registrar ou religar com dh link. dh link [nome] [--off] [dir] registra o repositório (padrão: a pasta atual) e, sem .harness/ interno, cria ~/.harness/projects/<nome>/ ou reaproveita a que existe. Dois repositórios com a mesma pasta-base: o segundo exige nome explícito. --off tira a entrada do mapa e não apaga a pasta do projeto. dh harness-path [dir] [--json] mostra o modo e a pasta resolvidos.
  5. Abrir o dashboard. Ver a seção Dashboard local; ele lê o mapa e as pastas globais.
  6. Mover ou renomear o repositório. O mapa fica velho: /dh:doctor mostra mode: none. Rode dh link na pasta nova (com o mesmo nome, para reaproveitar a pasta do projeto; a entrada do caminho antigo, que já não existe, é substituída).

Migrar de repo para global

1. mkdir -p ~/.harness/projects/<nome> && cp -r .harness/. ~/.harness/projects/<nome>/
2. git rm -r .harness   # ou rm -rf, se não era versionado; commite se for o caso
3. dh link <nome>; dh harness-path   # deve mostrar mode: global

Migrar de global para repo

1. cp -r ~/.harness/projects/<nome>/. .harness/   # na raiz do repositório
2. dh harness-path   # deve mostrar mode: repo (o interno vence); o projeto segue registrado
3. rm -rf ~/.harness/projects/<nome>   # só depois de conferir a cópia
Não existe comando de migração: são só essas linhas.

06Fluxos

O kit tem 13 agentes e 19 comandos. Você fala com o Coordenador; ele despacha os especialistas e guarda a autorização: nada é instalado, commitado, publicado ou implantado sem você autorizar.

Feature, do pedido à release

  1. /dh:discover <ideia>. O product-discovery pergunta uma coisa bloqueante por vez e escreve o PRD (Problema, Solução, Regras, Docs). Um document-validator revisa até 2 rodadas; você recebe o PRD depois de approved ou do teto.
  2. /dh:plan. O implementation-planner fatia o trabalho em PLAN.md e um TASK.md por fatia, cada um com a sua lane (backend, frontend, dados, infra ou de teste). O validador revisa o plano.
  3. /dh:build <ticket>. O builder implementa a fatia na lane do ticket, o qa-verifier escreve e roda os testes sobre o estado congelado, e um reviewer revisa. Até 6 rodadas de correção; qualquer edição invalida evidência e revisão. Repita por ticket. Se a mudança toca autenticação, dados, entrada ou execução, rode /dh:secure.
  4. /dh:review feature PRD-<n> e /dh:verify. A revisão final olha as costuras entre tickets contra o PRD inteiro, com uso da tela como cliente pelo QA (Playwright headless) quando há tela. Resultado: FEATURE APROVADA, REPROVADA ou BLOQUEADA. /dh:verify serve para ampliar a matriz de aceitação em qualquer ponto.
  5. /dh:document. O docs-guide atualiza o que a mudança exige. A documentação entra no mesmo PR, nunca em PR próprio.
  6. /dh:release. O release-manager monta o pacote de prontidão (versão, notas, compatibilidade, rollout, rollback). Ele para em "pronto para decisão": commit, push, tag e deploy só com a sua autorização.

Padrão de verificação: checagens determinísticas (dh validate, build, testes) mais 1 revisor na primeira entrada (claude quando reviewers.code o lista; sem o campo, só Claude). Reentrada da mesma tarefa avança uma entrada. O painel completo da etapa code só entra quando você pede. A etapa de segurança despacha a lista inteira em /dh:secure e não amplia a revisão de código. Detalhe em docs/adr/ADR-004-duvida-e-rotacao.md.

Tudo de uma vez: /dh:auto

/dh:auto aceita uma ideia, um PRD aprovado ou um PLAN.md aprovado, detecta a etapa inicial e faz um questionário único de 7 itens: etapa inicial, modo de decisão (a: decide e registra tudo; b: pergunta só decisão de produto ou contrato, o padrão; c: pergunta tudo), commit e push, PR, merge, tag e teto de gasto com evals (zero ou ausente significa nenhuma eval paga). Depois encadeia discover, plan e build numa branch só, com secure por fatia quando cabe, review ao fim e release. Para de vez diante de vulnerabilidade demonstrada, ação destrutiva, instalação não autorizada, teto de gasto ou de rodadas. O estado fica em .harness/tasks/AUTO-<n>/BRIEF.md; /dh:resume continua de onde parou.

Bug: /dh:fix

Passe o erro literal ou os passos de reprodução. O debugger reproduz, isola a causa (marcada como fato ou hipótese) e, se você autorizou mexer em arquivos, aplica a menor correção na origem do valor ruim, com teste de regressão visto falhar antes e passar depois. Depois entram qa-verifier e um reviewer. Sem reprodução, o resultado é "inconclusivo", nunca uma correção presumida.

Refatoração: /dh:refactor

Exige um problema estrutural nomeado e a linha de base dos checks antes de mexer. O builder (modo refactor) anda em passos pequenos e reversíveis; qualquer diferença observável é defeito. Feature nova vai para /dh:plan.

Verificação: /dh:verify

Com critérios de aceitação e uma mudança estável, o qa-verifier devolve uma matriz de passou, falhou ou não rodou, e, para interface, checa teclado, dois tamanhos de tela e estados de carga, erro e vazio, com capturas em .harness/tasks/<id>/evidence/.

Sessão longa: handoff, resume, consolidate-memory

  1. /dh:handoff grava objetivo, restrições, arquivos, decisões, evidências e o próximo passo em .harness/tasks/<id>/. Sem objetivo, ele para e pergunta.
  2. /dh:resume na sessão seguinte reconcilia o registro com a árvore (o repo-scout confere os arquivos) e continua só o que já foi autorizado. Onde os dois discordam, a árvore vence.
  3. /dh:consolidate-memory arquiva MEMORY.md em EPOCHAL.md, confere a cópia e só então encurta a memória. Ele pede que você confirme que nenhuma outra sessão está escrevendo.

Cuidar do kit: /dh:improve

Para um caso concreto em que o kit se comportou mal (prompt, esperado, observado). O harness-maintainer nomeia o ativo responsável, faz a menor edição nas fontes (.agents/, .skills/, .commands/, templates/, profiles/; nunca em dist/) e mede antes e depois com eval paga (rodar o /dh:improve já conta como o seu pedido de eval). Depois, /dh:doctor.

Entender antes de mexer: /dh:understand

Pergunte em forma de comportamento ("onde o reset de senha passa?"). O repo-scout devolve entradas, dependências e fluxo, só leitura.

07Configuração

.harness/project.yaml

Escrito pelo /dh:setup e ajustável à mão. Sem segredos nem caminhos absolutos. Campos:

  • language: en ou pt-br. Escolhe templates/<lang>/ para registros e artefatos e o idioma das respostas do Coordenador. Despachos, código e commits são sempre em inglês.
  • commands: test, lint, build, run, cada um com valor e origem; null significa "não adivinhar". Sem comando descobrível, o check é reportado como não rodado.
  • reviewers: opcional, por etapa (document, code, security; verify fica de fora). Cada entrada é claude, "cli:<binário>/<slug>" (timeout padrão de 15 minutos) ou {reviewer: "cli:<binário>/<slug>", timeout_minutes: <n>}. Ausente, o fluxo é só Claude.
language: pt-br
commands:
  test:
    value: go test ./...
    source: observed ci.yml
reviewers:
  document: [claude, "cli:codex/<slug>"]
  code: [claude]
  security: [claude]

.harness/local.yaml

Dados desta máquina: em binaries, onde achar cada CLI que não está no PATH; em models, os slugs medidos. Caminhos sempre relativos ao home (~/.grok/bin/grok) ou ao projeto, nunca o home expandido, para o arquivo servir em qualquer máquina. Um binário que não resolve deixa o revisor como não rodado, com o motivo. Modelo do arquivo: .skills/external-clis/references/local.yaml.example (no clone).

08Avançado

Planejamento em loop: /dh:plan-loop

Para feature nova, em vez de um plano só: o implementation-planner (Claude) disputa com um planejador de CLI externa em ondas. A rotação segue a ordem de reviewers.document; cada candidato é julgado pela lista completa de revisores, e o loop converge quando todos aprovam sem achado bloqueante, com pelo menos um revisor que não é Claude e não escreveu o candidato. Os tetos são plan_loop.wave_cap (padrão 6) e plan_loop.dispatch_cap (padrão 48) em project.yaml. Sem CLI elegível, cai no /dh:plan. Entregar o plano não autoriza construir.

Revisores de CLI externa e isolamento por clone

Listados em reviewers, rodam ao lado do Claude, ou no lugar dele. O binário é resolvido pelo PATH e, se falhar, por local.yaml; a resposta só vale com o sinal de veredito da etapa. Um binário com modo somente-leitura documentado e medido (hoje o codex) usa o próprio sandbox. Um sem esse modo (grok, opencode, mcode, claude como CLI) roda num clone descartável, e o agy como revisor na árvore viva com comparação de congelamento. O clone não é uma caixa de areia: escritas fora dele são detectadas na árvore viva, nunca impedidas, e escritas fora do projeto não são detectadas. Qualquer mudança detectada descarta o veredito. Um grok pode exigir uma regra de permissão Bash explícita em .claude/settings.local.json antes de o Coordenador conseguir despachá-lo. Detalhes por binário: skill external-clis.

Evals só a pedido

Medição paga de eval não faz parte do fluxo normal. Só roda quando você pede: direto, dentro do /dh:improve ou pelo teto de gasto do questionário do /dh:auto. Quando roda, é o mínimo que a mudança exige, uma execução por padrão.
