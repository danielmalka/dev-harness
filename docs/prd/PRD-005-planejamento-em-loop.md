## 1. Problema

Hoje `/dev-harness:plan` produz um único plano: `implementation-planner` escreve, `document-validator` (mais os revisores CLI que `reviewers.document` configurar) julga, e no máximo duas rodadas de correção decidem se o plano segue para o dono (`.commands/plan.md`; `.agents/coordinator.md` "Flows and completion"). Não existe hoje nenhum mecanismo que gere mais de um plano candidato para a mesma tarefa e deixe os revisores escolherem entre eles — a única forma de "melhorar" um plano é corrigi-lo dentro do mesmo ciclo de rodadas, nunca compará-lo com uma segunda tentativa independente.

O dono pediu, em 25/09/2026, um comando de planejamento em loop inspirado em duas referências (`docs/roadmap.html:1283-1287`; `.harness/tasks/UND-003/RESEARCH.md`): arquitetura de orquestração adversarial multi-wave e uma skill de orquestração em "waves". Nenhuma das duas referências tem um mecanismo técnico documentado — a primeira é um anúncio de ~350 palavras sem contagem de waves, papéis ou critério de parada; a segunda é uma página de marketplace, não a `SKILL.md` (`.harness/tasks/UND-003/RESEARCH.md` linhas 1-25). O desenho concreto deste comando vem inteiramente do grill de 25/09/2026 (`.harness/tasks/UND-003/GRILL.md`, decisões G1-G23 — G1-G17 na primeira passagem, G18-G23 na rodada 4, aberta pela primeira validação deste PRD), não das referências.

## 2. Resultado esperado

- Sinal 1: existe um comando que gera e compara planos concorrentes por wave, com três critérios de parada testáveis (teto de waves, convergência, teto de despachos) · hoje: 0 comandos assim · alvo: `/dev-harness:plan-loop` implementado com os três critérios de parada testáveis; a cobertura específica por eval fica para o plano de implementação decidir, não é um alvo deste PRD.
- Sinal 2: quando nenhuma CLI externa está disponível na máquina, o comando nunca finge rodar um loop · hoje: n/a (comando não existe) · alvo: 100% dos casos sem CLI caem no fluxo de `/dev-harness:plan`, com aviso explícito.
- Sinal 3: cada wave executada deixa evidência completa em disco (os planos candidatos, as revisões, o motivo da escolha) · hoje: n/a · alvo: `.harness/tasks/<id>/wave-N/` populado para toda wave, sem exceção, até a wave em que o loop parou, mais um relatório final no mesmo diretório-base.

## 3. Usuários e cenários

| Usuário | Cenário | Hoje | Depois |
|---|---|---|---|
| Dono | Quer um plano de implementação mais robusto que a correção de rodada única já entrega | Roda `/dev-harness:plan`; um único plano é corrigido até 2 vezes pelos mesmos revisores | Roda `/dev-harness:plan-loop`; a cada wave, dois planos concorrentes (um do `implementation-planner`, um de uma CLI de outro fornecedor) são julgados pelos mesmos revisores, e o melhor segue para a próxima wave |
| Dono, num projeto sem nenhuma CLI externa instalada/configurada | Quer comparar planos de fornecedores diferentes, mas não há nenhuma CLI resolvível nesta máquina | Não teria como comparar dois planos de fornecedores diferentes | Roda `/dev-harness:plan-loop`; o comando avisa que não há loop possível e executa o fluxo de `/dev-harness:plan` normalmente, sem alegar comparação nenhuma |
| Coordenador | Precisa decidir qual dos dois planos concorrentes de uma wave é o melhor | Não existe esse cenário hoje | Reaproveita os revisores já configurados para a etapa `document` (`reviewers.document`), aplicados a cada plano candidato; o plano com menos achados bloqueadores vence, sem que o Coordenador decida sozinho por critério subjetivo |
| Dono | O loop nunca converge (revisores continuam críticos a cada wave) | n/a | No teto de waves ou no teto de despachos, o que vier primeiro, recebe o melhor plano até ali com os bloqueadores ainda abertos listados como "teto atingido"; se em vez disso o loop converge, recebe o plano vencedor sem esse rótulo — convergência não é um teto |

## 4. Escopo

**Entra**
- RF-01 Novo comando `/dev-harness:plan-loop` (`.commands/plan-loop.md`, convenção observada em `.commands/plan.md`), decisão do dono (G10; recomendação do pesquisador tomada em vez de um modo de `/dev-harness:plan`). A saída é um plano — nunca código, QA ou uma fatia despachada —, mas o artefato final cobre o mesmo contrato completo que `/dev-harness:plan` já grava hoje, nos mesmos três locais (`.commands/plan.md` linhas 9 e 22): `PLAN.md` e os `TASK.md` por fatia, mais `PLAN.review.md`, sob `.harness/tasks/<PRD-id>/` quando deriva de um PRD ou `.harness/tasks/PLAN-<n>/` quando não deriva; ADRs para uma decisão de fronteira durável, quando aplicável, em `.harness/adr/ADR-<n>.md`; e as atualizações de `.harness/MEMORY.md` pelo Coordenador (achado Z1; decisão do Coordenador, revisão rodada 5). No caminho com loop, o mesmo diretório-base de tarefa recebe ainda os artefatos próprios das waves (RF-12): a persistência por wave e o relatório final (achado V3; decisão do Coordenador, revisão rodada 3). A execução do plano não é escopo deste comando; pertence ao futuro comando de execução autônoma de ponta a ponta (decisão do dono, G3; ainda não especificado neste kit). Autorização e fila de prioridade: ver seção 6.
- RF-02 Antes de abrir qualquer wave, o Coordenador verifica se há ao menos um binário de CLI externa resolvível a partir das entradas `cli:<binário>/<slug>` de `reviewers.document` (mesma resolução de binário que `external-clis` já define: `command -v` e, se ausente, `binaries.<binário>` em `.harness/local.yaml`), excluindo dessa verificação qualquer entrada `cli:claude/<slug>` enquanto o dev-harness roda como plugin do Claude Code (RF-05; decisão do dono (25/09/2026, AA1)): se as únicas entradas resolvíveis forem `cli:claude/<slug>`, isso conta como nenhuma CLI disponível para o loop. Sem nenhuma CLI resolvível (já contando essa exclusão), o comando informa explicitamente que não há loop e executa o fluxo de `/dev-harness:plan` sem alteração de mecanismo: um único plano do `implementation-planner`, ciclo normal de `document-validator`, teto de 6 rodadas de correção — o valor pós-migração, não o teto de 2 hoje escrito em `.agents/coordinator.md` e `.skills/document-review/SKILL.md`. **Pré-requisito de implementação**: este RF só pode ser implementado depois que o lote separado que sobe o teto padrão de correção do kit de 2 para 6 for entregue (decisão da rodada 4 do grill, tomada pelo Coordenador, consistente com a decisão do dono de 25/09/2026 registrada em `CLAUDE.md`); a implementação de `/dev-harness:plan-loop` não redefine esse teto por conta própria, só consome o valor que o outro lote já vai ter fixado. O motivo por trás dessa regra está registrado no grill: duas gerações da mesma IA não valem como comparação entre planos (decisão do dono, G6 — registro do grill).
- RF-03 Com ao menos uma CLI disponível, cada wave produz exatamente dois planos candidatos para a mesma tarefa: um do `implementation-planner` (Claude), um da CLI da vez (decisão do dono, G6). A wave 1 é sempre escrita de forma cega — nenhum dos dois lê o rascunho do outro antes de terminar. A partir da wave 2, os dois escritores partem do plano vencedor da wave anterior (RF-08) mas continuam sem ver o novo rascunho um do outro enquanto escrevem. Isto é uma decisão explícita do dono, não uma inferência de design (decisão do dono, G23 — registro do grill).
- RF-04 A chamada à CLI que escreve o plano candidato reaproveita a mecânica já definida em `.skills/external-clis/SKILL.md` para uma chamada somente-leitura: resolução de binário, modo somente-leitura do binário quando existir, e a checagem de congelamento do workspace (`git status --porcelain -uall` + `git hash-object` por caminho, antes e depois da chamada). A CLI devolve o texto do plano como resposta; o Coordenador é quem grava o arquivo em disco — a CLI nunca escreve diretamente no repositório (decisão do dono, G15 — registro do grill). O prompt que a CLI recebe é montado a partir do corpo de `.agents/implementation-planner.md` (sem frontmatter), do texto da skill `implementation-planning` e do contexto da wave (a tarefa, o plano vencedor anterior quando existir, os achados bloqueadores ainda abertos contra ele), e carrega, verbatim, três blocos: a instrução de não escrever nenhum arquivo (a CLI só devolve texto), uma cláusula anti-delegação equivalente à de `external-clis` mas com a redação ajustada para uma tarefa de planejamento em vez de revisão (redação exata fixada no lote de implementação), e o bloco "reading is allowed" já publicado por `external-clis`. Como essa chamada devolve texto de plano, não um veredito de revisão, ela não tem uma linha de sinal como `## Verdict`/`## Findings`; a chamada é falha de transporte — e o plano da wave é descartado (consequência em RF-15, G20) — nos mesmos casos já definidos para um revisor CLI (exit não-zero, timeout, alteração detectada pela checagem de congelamento) mais um critério próprio de planejamento: resposta sem conteúdo de plano reconhecível — o sinal mínimo são as seções exigidas pelo formato de `implementation-planning` (objetivo e fatias); a checagem exata fica para o lote de implementação (achado N4, revisão rodada 2).
- RF-05 A lista de rotação são as entradas `cli:<binário>/<slug>` resolvíveis de `reviewers.document` (excluindo `claude`, o revisor Claude nativo), na ordem em que aparecem na lista, apurada uma única vez pela checagem de disponibilidade do início do loop (RF-02) — ela não é recalculada a cada wave. Enquanto o dev-harness roda como plugin do Claude Code, qualquer entrada `cli:claude/<slug>` também é excluída dessa lista: como tudo já roda em cima do Claude, essa CLI não acrescenta um segundo fornecedor à comparação (decisão do dono (25/09/2026, AA1)). Quando o kit rodar num host que não seja o Claude Code, `cli:claude/<slug>` volta para a lista de rotação — esse retorno é trabalho de um lote futuro, fora do escopo deste PRD; esta frase só registra a condição (decisão do dono (25/09/2026, AA1)). Sejam `k` entradas nessa lista — já sem `claude` nem, enquanto essa condição valer, `cli:claude/<slug>` —, indexadas a partir de 0; a CLI primária da wave `N` é a entrada de índice `(N−1) mod k` (decisão do dono, G19 — registro do grill: reaproveitar `reviewers.document`, girando por qualquer quantidade de CLIs, não só duas; fórmula fixada pelo Coordenador — achado T1; decisão do Coordenador derivada de G19–G21, revisão rodada 2). O pool de CLIs planejadoras é exatamente esse — nenhuma chave nova em `.harness/project.yaml` — porque o dono já autorizou esses binários e slugs para trabalho na etapa `document` (`.agents/coordinator.md` "Model selection": a lista em `reviewers:` já é a autorização explícita do dono para o provedor e o modelo daquela etapa). Uma entrada que deixa de resolver bem depois do início do loop, exatamente na sua vez, é tratada como no RF-15: a vez passa para a próxima entrada da mesma lista de rotação, sem recalcular a lista a partir de `reviewers.document` outra vez (achado T1; decisão do Coordenador derivada de G19–G21, revisão rodada 2).
- RF-06 Os dois planos candidatos de uma wave são julgados pelos revisores já configurados para a etapa `document` (`reviewers.document` em `.harness/project.yaml`, o mesmo mecanismo que já aplica a `PLAN.md` hoje — `.agents/coordinator.md` "Flows and completion": "A document that becomes a contract — the PRD, the plan... — passes through document-validator against its source"), aplicados uma vez a cada candidato de forma independente — uma wave é uma única passada de avaliação, nunca um ciclo de correção aninhado. Um veredito `changes required` de qualquer revisor não redespacha o planejador (Claude ou CLI) dentro da mesma wave: os achados bloqueadores ainda abertos só alimentam a wave seguinte, como ponto de partida do refinamento (RF-08). O ciclo de correção de `/dev-harness:plan` (rodadas, `document-validator` revalidando o mesmo documento) se aplica só ao caminho sem CLI (RF-02); dentro do loop, uma wave de dois candidatos gasta `2×R` despachos de revisão — R revisores julgando cada um dos dois planos —, e uma wave de candidato único (RF-15) gasta `R` — os mesmos R revisores julgando o único plano —; em ambos os casos soma-se qualquer despacho de hand-off do RF-15 (achado V4; decisão do Coordenador derivada de G5, revisão rodada 3; achado W3, revisão rodada 4). Cada candidato recebe sua própria contagem de achados, mesclada entre todos os revisores da etapa exatamente como `.agents/coordinator.md` "External CLI reviewers" já define para qualquer documento revisado por múltiplos revisores. Quando uma wave tiver um único candidato (RF-15, porque nenhuma CLI restou disponível), os revisores avaliam esse único plano do mesmo jeito; não há comparação nem vencedor por contagem relativa nessa wave — o próprio plano segue como base, sujeito aos mesmos critérios de parada (RF-09).
- RF-07 O plano com menos achados bloqueadores vence a wave (decisão do dono, G7 — registro do grill). Em caso de empate na contagem de achados bloqueadores, vence o plano com menos achados no total (bloqueadores mais não-bloqueadores); se esse total também empatar, vence o plano do `implementation-planner` (decisão do dono, G18). O Coordenador não escolhe por critério próprio em nenhum dos três passos; a contagem decide.
- RF-08 A wave seguinte parte do plano vencedor: a partir da wave 2, ambos os escritores (o `implementation-planner` e a CLI da vez) recebem o plano vencedor da wave anterior e os achados bloqueadores ainda abertos contra ele como ponto de partida, e o refinam de forma independente — nenhum dos dois vê o novo rascunho do outro enquanto escreve (G23; ver RF-03).
- RF-09 O loop para na primeira das três condições que ocorrer:
  - **Teto de waves**: padrão 6, fixado diretamente por este PRD — não herdado em tempo de execução do teto kit-wide de correção (achado N1, revisão rodada 2; decisão do dono, G4 e G5 — registro do grill: os revisores são exigentes, então um teto de 2 ou 3 waves raramente bastaria, e o teto conta waves, cada wave sendo uma rodada de revisão). Configurável em `.harness/project.yaml` (chave proposta `plan_loop.wave_cap`).
  - **Convergência**: todo revisor da etapa `document` que efetivamente rodou aprova, sem nenhum achado bloqueador, o plano vencedor da wave corrente, e ao menos um desses revisores é de um fornecedor diferente de Claude (decisão do dono, G9 combinada com a emenda da rodada 4, G22 — registro do grill). Achados não-bloqueadores não impedem a convergência. Um revisor not-run (binário ausente, falha de transporte) não conta nem a favor nem contra a convergência — só os revisores que de fato rodaram entram na conta.
  - **Teto de despachos**: verificado antes de abrir cada wave, nunca no meio dela. Uma wave "cabe" quando o teto restante for maior ou igual a `2 + 2×R`, onde `R` é o número de revisores configurados em `reviewers.document` — 2 despachos de planejador (Claude e a CLI da vez) mais `2×R` despachos de revisão (R revisores julgando cada um dos dois planos candidatos) (achado T2; decisão do Coordenador derivada de G19–G21, revisão rodada 2). Uma wave que não cabe não é aberta, e o loop para por teto de despachos nesse ponto; uma wave já aberta sempre termina até o fim, mesmo que hand-offs (RF-15) façam seus despachos ultrapassarem essa reserva — eles também contam para o teto (decisão do dono, G21 — registro do grill). Despachos que falham ou ficam not-run contam para o teto do mesmo jeito que um despacho bem-sucedido (G21). Padrão 48, contando todo despacho de planejador (Claude ou CLI) e de revisor (Claude ou CLI) somado em todas as waves da execução; configurável em `.harness/project.yaml` (chave proposta `plan_loop.dispatch_cap`) (decisão do dono, G8 e G16 — registro do grill).
- RF-10 O relatório final apresenta uma estimativa em dólares derivada da contagem de despachos realizados (decisão do dono, G8 — registro do grill). A base de cálculo dessa estimativa (por exemplo, um custo médio observado por despacho, ou um valor por modelo/fornecedor) fica para o lote de implementação definir; este PRD só exige que a estimativa apareça no relatório, não o método exato.
- RF-11 Quando o loop parar por teto de waves ou por teto de despachos sem ter convergido, o plano entregue ao dono é o melhor vencedor entre todas as waves já executadas — não necessariamente o vencedor da última wave —, usando o mesmo critério de desempate do RF-07 (menos achados bloqueadores; empate, menos achados no total) e, se ainda empatado, a wave mais recente prevalece (achado V2; decisão do Coordenador derivada de G11 e G18, revisão rodada 3). Os achados bloqueadores ainda abertos contra esse plano ficam listados sob o rótulo "teto atingido" (decisão do dono, G11 — registro do grill). Esse rótulo nunca aparece quando o loop para por convergência — convergência é sucesso, não um teto. RF-12 grava esse plano como `PLAN.md`, e sua revisão mesclada vira o `PLAN.review.md` de nível base.
- RF-12 Toda wave executada persiste em `.harness/tasks/<id>/wave-N/` (decisão do dono, G12): os planos candidatos da wave (dois, ou um só no caso RF-15), os relatórios de revisão correspondentes (cada um já mesclando os revisores Claude/CLI da etapa `document` como RF-06 descreve) e um registro de qual candidato venceu e por quê. `<id>` segue a mesma convenção que `/dev-harness:plan` já usa para `PLAN.md` (`.commands/plan.md`; `docs/prd/PRD-004-evals-executaveis-e-higiene.md` RF-10): o `<PRD-id>` quando o loop deriva de um PRD, `PLAN-<n>` sequencial quando não deriva. Ao final da execução (por convergência, teto de waves ou teto de despachos), o mesmo diretório-base recebe também: o plano vencedor — o vencedor da wave final quando o loop convergiu, ou o melhor vencedor entre todas as waves conforme RF-11 quando parou por um teto — gravado como `PLAN.md` com seus `TASK.md`, no mesmo formato que `/dev-harness:plan` já grava hoje; um `PLAN.review.md` de nível base com a revisão mesclada desse plano — o mesmo arquivo que consumidores de `/dev-harness:plan` já esperam encontrar ali (achado T3; decisão do Coordenador derivada de G19–G21, revisão rodada 2); e um relatório final (nome exato do arquivo a definir no lote de implementação) contendo o motivo da parada, a contagem total de despachos, a estimativa em dólares (RF-10) e, só quando o loop parou sem convergir, os achados bloqueadores ainda abertos sob o rótulo "teto atingido" (RF-11). Fora desse diretório-base: quando o plano vencedor tiver uma decisão de fronteira durável, o Coordenador grava o ADR correspondente em `.harness/adr/ADR-<n>.md`; e o Coordenador atualiza `.harness/MEMORY.md`, do mesmo jeito que já faz para `/dev-harness:plan` (achado Z1, revisão rodada 5; achado W2, revisão rodada 4). Esta enumeração de artefatos vale para o caminho com loop; o caminho sem CLI (fallback) segue a persistência completa descrita no RF-02/AC-03.
- RF-13 Cada planejador despachado numa wave — o `implementation-planner` e a CLI da vez, quando houver uma (RF-15 cobre a wave com um único candidato) — conta como um especialista concorrente contra o teto de dois definido em `.agents/coordinator.md` (Procedure item 5), exatamente como já vale hoje para um revisor CLI ("An external CLI reviewer counts as one concurrent specialist against this cap, exactly like a Claude specialist"). O texto atual dessa regra fala só em revisor; este PRD amplia o mesmo teto para cobrir também um planejador CLI (ver seção 6, Contratos).
- RF-14 O comando nunca despacha uma fatia de implementação, QA ou build ao terminar, e a entrega do plano não autoriza, por si só, o início dessa implementação (G17; ver seção 6, Autorização). O próximo passo nomeado no relatório final é `/dev-harness:build` sobre a primeira fatia pronta do plano vencedor, ou o futuro comando de execução autônoma quando ele existir.
- RF-15 Quando o plano candidato da entrada da vez for descartado por falha de transporte numa wave (RF-04) — inclusive quando essa entrada deixou de resolver (RF-05) —, o Coordenador inicia uma varredura circular pelas demais entradas da lista de rotação, nunca repetindo a entrada primária que já falhou: começa na entrada seguinte à primária da wave e tenta, em ordem, cada uma das outras `k−1` entradas no máximo uma vez nessa wave, voltando ao início da lista ao chegar no fim, sem jamais tentar de novo a primária que falhou (achado X1; decisão do Coordenador derivada de G20, revisão rodada 4). Com `k = 1` (uma única CLI configurada, que é sempre a primária), não há outra entrada para tentar: a falha vai direto para uma wave de candidato único, sem varredura nenhuma. A wave roda com um único candidato — o plano do `implementation-planner` — quando a primária falha e todas as demais `k−1` entradas também falham nela, ou quando `k = 1`; nesse caso não há comparação, o processo não trava, e a wave conta normalmente para o teto de waves (decisão do dono, G20 — registro do grill). Esse hand-off nunca move o cursor de rotação: a CLI primária da wave seguinte continua calculada só pelo número dela (entrada de índice `N mod k`, 0-indexada, para a wave `N+1`), nunca pelo ponto em que a varredura desta wave parou (achado T1; decisão do Coordenador derivada de G19–G21, revisão rodada 2).

**Não entra**
- Execução do plano vencedor. Este comando produz plano, nunca código, QA ou revisão de código (decisão do dono, G3).
- Um "modo" dentro de `/dev-harness:plan`. É um comando novo (decisão do dono, G10).
- Mais de um plano por CLI dentro da mesma wave, ou mais de dois planos candidatos julgados numa única wave — cada wave sempre compara o plano do `implementation-planner` com o de uma única CLI da vez (RF-03, RF-05), mesmo quando o pool de `reviewers.document` tem mais de duas entradas (decisão do dono, G6 e G19 — registro do grill; achado não-bloqueador, revisão rodada 3).
- O lote separado que sobe o teto padrão de correção do kit de 2 para 6 em `.agents/coordinator.md` e nas skills de revisão. Esse lote é um pré-requisito de implementação deste PRD (RF-02, seção 6), não parte do escopo dele — este PRD só consome o valor 6 já decidido pelo dono (`CLAUDE.md`, 25/09/2026), não migra o texto do kit.
- Instalar, autenticar ou atualizar qualquer CLI. Igual a `external-clis`: binário ausente é not-run, nunca provisionado.
- Fallback automático de fornecedor de CLI para um binário fora da lista configurada em `reviewers.document` (diferente do revezamento de RF-05/RF-15, que só usa binários já configurados). Uma CLI que falha vira not-run naquela wave; não há substituição por um binário não configurado, seguindo a mesma regra que `docs/prd/PRD-003-revisao-em-pares-por-cli.md` já fixou para revisores.

## 5. Critérios de aceite

- AC-01 (RF-01, RF-12) No caminho com loop (ao menos uma CLI resolvível), quando `/dev-harness:plan-loop` terminar, então os artefatos produzidos são exatamente: por wave executada, os planos candidatos, os relatórios de revisão e o registro do vencedor sob `.harness/tasks/<id>/wave-N/`; ao final, sob o mesmo diretório-base de tarefa, o plano vencedor (`PLAN.md` e seus `TASK.md`), o `PLAN.review.md` de nível base com a revisão mesclada do plano vencedor final, e o artefato próprio do loop — um relatório final com o motivo da parada, a contagem de despachos, a estimativa em dólares e, só quando o loop parou sem convergir, os bloqueadores ainda abertos sob "teto atingido"; fora desse diretório-base, um ADR em `.harness/adr/ADR-<n>.md` quando o plano vencedor tiver uma decisão de fronteira durável, e as atualizações de `.harness/MEMORY.md` pelo Coordenador (achado V3, revisão rodada 3; achado W1, revisão rodada 4; achado Z1, revisão rodada 5). Nenhuma fatia de implementação, QA ou revisão de código é despachada como parte deste comando. O caminho sem CLI (fallback) tem sua própria persistência — ver AC-03.
- AC-02 (RF-02) Quando nenhum binário de CLI configurado em `reviewers.document` estiver resolvível nesta máquina, então o comando informa explicitamente que não há loop disponível e executa o fluxo de `/dev-harness:plan`: um único plano, ciclo normal de `document-validator`, teto de 6 rodadas de correção — o valor que o lote pré-requisito (RF-02) já terá fixado.
- AC-03 (RF-02) Quando o comando cair no fluxo sem loop por ausência de CLI, então nenhum diretório `wave-N/` é criado; a persistência segue o contrato completo já vigente de `/dev-harness:plan`: `PLAN.md`, os `TASK.md` por fatia, ADRs quando aplicável, `PLAN.review.md`, e as atualizações de memória feitas pelo Coordenador — nada mais, nada menos (achado T3; decisão do Coordenador derivada de G19–G21, revisão rodada 2).
- AC-04 (RF-03, RF-08) Quando o loop tiver ao menos uma CLI disponível, então a wave 1 produz dois planos candidatos escritos sem que nenhum dos dois leia o rascunho do outro; a partir da wave 2, os dois escritores recebem o plano vencedor da wave anterior como ponto de partida, mas continuam sem ver o novo rascunho um do outro enquanto escrevem.
- AC-05 (RF-04) Quando a CLI planejadora for despachada numa wave, então o prompt que ela recebe contém, verbatim, a instrução de não escrever nenhum arquivo, a cláusula anti-delegação redigida para planejamento e o bloco "reading is allowed"; a chamada roda no modo somente-leitura do binário quando ele existir, e a checagem de congelamento (`git status --porcelain -uall` + `git hash-object` por caminho, antes e depois) é aplicada; qualquer alteração detectada no workspace descarta o plano dessa CLI na wave, reverte a alteração e marca a CLI not-run por falha de transporte — o Coordenador é o único gravador do plano (achado N3, revisão rodada 2).
- AC-06 (RF-05) Quando `k` entradas `cli:<binário>/<slug>` estiverem configuradas e resolvíveis em `reviewers.document` no início do loop — excluindo qualquer `cli:claude/<slug>` enquanto o dev-harness roda como plugin do Claude Code (decisão do dono (25/09/2026, AA1)) — e `k` ≥ 1 depois dessa exclusão, então a wave 1 usa a entrada de índice 0 da lista de rotação para escrever o plano concorrente, a wave 2 usa a entrada de índice 1, e assim por diante — a CLI primária da wave `N` é sempre a entrada `(N−1) mod k`, a mesma fórmula do RF-05, sem restatements divergentes. Quando as únicas entradas resolvíveis forem `cli:claude/<slug>` (`k` = 0 depois da exclusão), o comando cai no fluxo sem loop (RF-02).
- AC-07 (RF-06, RF-07) Quando os dois planos candidatos de uma wave estiverem prontos, então os revisores configurados para a etapa `document` avaliam cada candidato de forma independente, e o candidato com menos achados bloqueadores é registrado como vencedor; em caso de empate nos achados bloqueadores, vence o plano com menos achados no total; se esse total também empatar, vence o plano do `implementation-planner`.
- AC-08 (RF-08) Quando uma wave tiver um vencedor, então a wave seguinte recebe esse plano e seus achados bloqueadores ainda abertos como ponto de partida para os dois escritores.
- AC-09 (RF-09, teto de waves) Quando o número de waves executadas atingir o teto configurado (padrão 6) sem que a convergência ou o teto de despachos tenham ocorrido antes, então o loop para por teto de waves.
- AC-10 (RF-09, convergência) Quando todo revisor da etapa `document` que efetivamente rodou aprovar, sem achados bloqueadores, o plano vencedor de uma wave, e ao menos um desses revisores for de um fornecedor diferente de Claude, então o loop para imediatamente por convergência, mesmo que o teto de waves ainda não tenha sido atingido; um revisor not-run não conta nem a favor nem contra essa convergência.
- AC-11 (RF-09, teto de despachos) Quando o teto de despachos configurado (padrão 48) for verificado antes de abrir uma wave, e o teto restante for menor que `2 + 2×R` (R = número de revisores configurados em `reviewers.document`), então essa wave não é aberta e o loop para por teto de despachos; uma wave já aberta sempre termina até o fim, mesmo que hand-offs (RF-15) ultrapassem essa reserva, e despachos que falham ou ficam not-run contam para o teto do mesmo jeito que um despacho bem-sucedido. Exemplo (achado T2, revisão rodada 2): com R = 3 revisores configurados, uma wave reserva `2 + 2×3 = 8` despachos do teto; um teto restante de 7 impede a abertura dessa wave, um teto restante de 8 ou mais permite.
- AC-12 (RF-11, RF-12) Quando o loop parar por teto de waves ou por teto de despachos sem ter convergido, então o plano entregue é o vencedor com menos achados bloqueadores entre todas as waves já executadas — não necessariamente o da última wave —, com empate resolvido por menos achados no total e, se ainda persistir, pela wave mais recente; os achados bloqueadores ainda abertos contra esse plano ficam listados sob o rótulo "teto atingido"; esse rótulo não aparece no relatório quando o loop para por convergência.
- AC-13 (RF-10) Quando o loop terminar, por qualquer um dos três critérios, então o relatório final inclui uma estimativa em dólares derivada da contagem total de despachos realizados; a base de cálculo dessa estimativa é definida no lote de implementação, não por este PRD.
- AC-14 (RF-12) Quando uma wave terminar, então `.harness/tasks/<id>/wave-N/` contém os planos candidatos dessa wave, os relatórios de revisão correspondentes e o registro de qual venceu e por quê, para toda wave executada até a que encerrou o loop; ao final da execução, o mesmo diretório-base também contém o `PLAN.md`/`TASK.md` vencedor, o `PLAN.review.md` de nível base, e o relatório final — todos descritos em RF-12 —, e, fora desse diretório-base, um ADR em `.harness/adr/ADR-<n>.md` existe quando o plano vencedor tiver uma decisão de fronteira durável, e `.harness/MEMORY.md` está atualizado pelo Coordenador (achado Z1, revisão rodada 5).
- AC-15 (RF-13) Quando um planejador CLI e o `implementation-planner` forem despachados na mesma wave, então cada um conta como um especialista concorrente contra o teto de dois definido em `.agents/coordinator.md`, exatamente como já vale para um revisor CLI hoje.
- AC-16 (RF-14) Quando o loop terminar com um plano vencedor, então o relatório nomeia `/dev-harness:build` sobre a primeira fatia pronta (ou o futuro comando de execução autônoma) como próximo passo, nenhuma fatia é despachada automaticamente por este comando, e a entrega do plano não é lida como autorização para começar essa implementação.
- AC-17 (RF-15) Quando o plano candidato da entrada da vez for descartado por falha de transporte no meio de uma wave, então o Coordenador varre circularmente as outras `k−1` entradas da lista de rotação, a partir da entrada seguinte à primária, tentando cada uma no máximo uma vez e sem jamais retentar a primária que já falhou; com `k = 1`, não há varredura e a falha vai direto para uma wave de candidato único. A wave roda com um único candidato — o plano do `implementation-planner`, sem comparação e sem travar o processo — quando a primária falha e todas as demais entradas também falham nela, ou quando `k = 1`, e essa wave conta normalmente para o teto de waves.
- AC-18 (RF-05, RF-15) Quando uma entrada configurada em `reviewers.document` estava resolvível no início do loop mas deixa de resolver exatamente na sua vez (por exemplo, o binário foi removido da máquina entre waves), então ela é tratada como no RF-15: a vez passa à próxima entrada da lista de rotação apurada em RF-02, dentro da mesma wave, sem recalcular essa lista a partir de `reviewers.document` de novo (achado T1, revisão rodada 2).
- AC-19 (RF-05, RF-15) Quando uma wave tiver um ou mais hand-offs (RF-15, entradas descartadas dentro da mesma wave), então o cursor de rotação não se move por causa disso: a CLI primária da wave seguinte continua sendo calculada só pelo número dela — a entrada `N mod k`, 0-indexada, para a wave `N+1` — nunca pelo ponto em que o hand-off da wave atual parou (achado T1, revisão rodada 2).
- AC-20 (RF-06) Quando um revisor devolver `changes required` para um candidato de uma wave, então o Coordenador não redespacha o planejador (Claude ou CLI) dentro dessa mesma wave; os achados bloqueadores ainda abertos alimentam a wave seguinte (RF-08). Uma wave com dois candidatos gasta `2×R` despachos de revisão; uma wave de candidato único (RF-15) gasta `R` (R = revisores configurados em `reviewers.document`); em ambos os casos soma-se qualquer despacho de hand-off do RF-15 (achado V4, revisão rodada 3; achado W3, revisão rodada 4).

## 6. Restrições e impacto técnico

- Dados: `.harness/project.yaml` ganha uma seção opcional `plan_loop:` com `wave_cap` (padrão 6) e `dispatch_cap` (padrão 48); sem a seção, os padrões valem. Nenhuma migração de dado existente. `.harness/tasks/<id>/wave-N/` é o diretório novo por wave; segue a mesma convenção de `.harness/tasks/<id>/` que `PLAN.md`/`TASK.md` já usam, com um relatório final adicional no diretório-base (RF-12).
- Contratos: `.agents/coordinator.md` "Procedure" item 5 (teto de dois especialistas concorrentes) e "External CLI reviewers" hoje falam só em revisor CLI ("An external CLI reviewer counts as one concurrent specialist against this cap"); este PRD exige que o mesmo teto e o mesmo mecanismo de congelamento cubram também um planejador CLI. `.skills/external-clis/SKILL.md` hoje descreve seu escopo, em "When not to use", como "review stages only; a CLI never writes production code through this skill" — um plano não é código de produção, mas é conteúdo novo que a CLI escreve, não uma revisão de conteúdo existente; o texto dessa skill (e o de `.skills/implementation-planning/SKILL.md`, fonte do corpo do prompt de planejamento por RF-04) precisa nomear esse novo tipo de chamada no lote que implementar este PRD. Nenhum contrato de API externo é afetado.
- Segurança: a CLI planejadora nunca escreve arquivo diretamente (RF-04); o Coordenador é o único gravador, como já vale para `.harness/local.yaml` e para os relatórios de revisão. A cláusula anti-delegação e o bloco "reading is allowed" de `external-clis` se aplicam à chamada de planejamento do mesmo jeito que a uma chamada de revisão. A classificação de falha de transporte dessa chamada reaproveita os critérios já usados para um revisor CLI (exit não-zero, timeout, alteração de workspace detectada pela checagem de congelamento) mais a ausência de conteúdo de plano reconhecível (RF-04); não há um sinal de veredito dedicado como `## Verdict`/`## Findings`, porque a chamada devolve um plano, não uma revisão.
- Operação: nenhuma CLI nova é instalada, autenticada ou atualizada; o loop só usa binários já resolvíveis por `external-clis`, do mesmo pool já configurado em `reviewers.document` (RF-05). Sem CLI resolvível, o comando nunca finge rodar em loop (RF-02).
- Stack e dependências: nenhuma dependência nova de build.
- Prazo / custo: cada wave multiplica o número de despachos de revisão (planos revisados independentemente); o teto de despachos (RF-09) e a estimativa em dólares (RF-10) existem justamente para tornar esse custo visível e limitado.
- Pré-requisito: o fallback sem CLI (RF-02) depende da entrega prévia do lote separado que sobe o teto padrão de correção do kit de 2 para 6 (decisão do dono de 25/09/2026, `CLAUDE.md`; ver "Não entra"), porque ele reaproveita o teto de correção do `/dev-harness:plan` pós-migração. `plan_loop.wave_cap` (RF-09) não depende desse lote: seu padrão de 6 é fixado diretamente por este PRD e só coincide com o valor kit-wide porque o dono decidiu os dois com a mesma razão (G4) — não há herança em tempo de execução entre um teto e o outro (achado N1, revisão rodada 2).
- Autorização: a aprovação deste PRD autoriza o contrato, nunca a implementação. Por decisão do dono, a implementação deste comando permanece a terceira prioridade da fila de trabalho, atrás de prioridades já registradas (decisão do dono, G17 — registro do grill).

## 7. Alternativas descartadas

| Alternativa | Por que não |
|---|---|
| Modo dentro de `/dev-harness:plan` em vez de comando novo | Mistura dois fluxos com garantias diferentes (teto de 2 rodadas de correção vs. teto de 6 waves, um plano vs. dois candidatos); o dono decidiu comando novo (G10) |
| Gerar sempre dois planos, mesmo sem CLI configurada, comparando duas gerações do próprio Claude | O dono rejeitou essa opção: duas gerações da mesma IA não valem como comparação entre planos (decisão do dono, G6 — registro do grill) |
| Convergência por aprovação de qualquer revisor, não a totalidade dos que rodaram | Pararia cedo demais e contradiria o motivo do dono para subir o teto a 6 (decisão do dono, G4 — registro do grill: os revisores são exigentes); G9 combinado com G22 exige que todo revisor que efetivamente rodou aprove, com ao menos um de outro fornecedor |
| Loop sem teto de despachos, só teto de waves e convergência | Custo não limitado quando uma wave gasta muitos despachos de revisão; G8/G16 fixam um teto de despachos configurável |
| Cadeia de fallback automática para uma CLI fora da lista configurada | Mesma razão já registrada em PRD-003: esconderia do dono qual CLI de fato escreveu o plano; uma CLI que falha vira not-run e a vez passa só para outra CLI já configurada (RF-15), nunca para um binário não autorizado |

## 8. Riscos e decisões pendentes

- Risco: julgar planos candidatos por wave multiplica o número de despachos de revisão em relação a `/dev-harness:plan` hoje · mitigação: RF-09 (teto de despachos) limita o gasto total, e RF-10 exige a estimativa em dólares no relatório final.
- Risco: os revisores da etapa `document` (`document-validator` e os revisores CLI configurados) podem divergir de julgamento entre execuções, e este PRD os despacha até `2×R` vezes por wave (RF-06) · mitigação: nenhuma nova além do que `document-review`/`external-clis` já fazem — os mesmos revisores, sem alteração de critério; o teto de despachos e o relatório final tornam o custo dessa variabilidade visível (achado não-bloqueador, revisão rodada 3).
