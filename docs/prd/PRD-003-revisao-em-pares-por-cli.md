## 1. Problema

Hoje toda revisão independente do kit (`document-validator`, `code-reviewer`, `security-reviewer`) é sempre um agente Claude despachado pelo Coordenador — nunca há uma segunda opinião de outro provedor. Fora do dev-harness, o dono já usa uma skill pessoal (`~/.claude/skills/fleet-clis`) para invocar CLIs de outras IAs instaladas nesta máquina (`agy`, `codex`, `grok`, `opencode`, `mcode`, `claude`) de forma headless, com flags e slugs medidos empiricamente. Essa skill não está integrada ao dev-harness: não reaproveita os prompts de `.agents/<role>.md`, não tem lugar em `.harness/` para declarar quais revisores rodam em qual etapa, e carrega caminhos absolutos e slugs de modelo específicos desta máquina (`gotchas.md` medido em 2026-08-30), o que viola a regra de portabilidade de `profiles/README.md` ("no absolute paths, tokens or machine binaries in `.harness/project.yaml`").

O histórico de `gotchas.md` da skill pessoal (45 entradas de 2026-08-18 a 2026-09-20) mostra que chamadas a CLI externa falham com frequência de forma silenciosa: exit 0 sem `VERDICT`, timeout sem saída, e ao menos um caso real de uma CLI invocando outra por conta própria dentro do mesmo checkout (2026-09-17: `codex exec -m gpt-5.6-luna` como implementer abriu sozinho um `opencode run -m opencode-go/glm-5.3`, delegando a implementação sem ter sido instruído a isso). Sem um contrato formal no kit para distinguir "falha de transporte" de "veredito real", esse padrão de falha vazaria para o ciclo de revisão do Coordenador.

## 2. Resultado esperado

- Sinal 1: pelo menos uma etapa de revisão do kit (código, PRD/documento ou segurança) pode ser configurada, por projeto, para rodar com N revisores em paralelo — Claude e/ou CLI externa — em vez de sempre um único agente Claude · hoje: 0 etapas configuráveis · alvo: as três etapas de revisão existentes (`document-review`, `code-review`, `security-review`) suportam a configuração.
- Sinal 2: quando um binário de CLI configurado está ausente na máquina, o Coordenador sempre registra uma entrada explícita de not-run e segue com os revisores disponíveis, nunca finge que a etapa não foi pedida · hoje: n/a (não existe o conceito) · alvo: 100% dos casos cobertos pelos casos de eval deste PRD.
- Sinal 3: zero caminho absoluto, token ou slug medido nesta máquina aparece em `.skills/`, `.agents/`, `.commands/` ou `templates/` depois da mudança · hoje: fleet-clis pessoal tem esses dados hardcoded · alvo: 0 ocorrências, verificável por grep.

## 3. Usuários e cenários

| Usuário | Cenário | Hoje | Depois |
|---|---|---|---|
| Dono | Quer uma segunda opinião de outro provedor na revisão de código de um projeto | Roda `fleet-clis` manualmente, fora do dev-harness, sem registro em `.harness/` nem reaproveito do prompt de `code-reviewer` | Declara em `reviewers:` de `.harness/project.yaml` que a etapa `code` usa `claude` + `cli:codex/gpt-5.6-sol` em paralelo; o Coordenador despacha os dois com o mesmo prompt de `.agents/code-reviewer.md` e mescla o veredito |

| Coordenador | Uma CLI configurada não está instalada nesta máquina (projeto foi clonado numa máquina diferente da do dono) | n/a | Detecta a ausência do binário, registra o revisor como not-run com o motivo, e segue a etapa só com os revisores disponíveis |
| Coordenador | Dois revisores discordam sobre o mesmo trecho | n/a | Relatório mesclado marca "disagreement", cita os dois vereditos e não decide sozinho qual prevalece |

## 4. Escopo

**Entra**
- RF-01 Skill do kit `external-clis` (nome proposto, inglês, em `.skills/`), portada e generalizada de `~/.claude/skills/fleet-clis`, ensinando o Coordenador e os papéis de revisão a invocar CLIs de outras IAs de forma headless: resolver o binário (`command -v` e, se ausente, o caminho declarado em `.harness/local.yaml`, relativo ao home ou ao projeto), escrever o prompt em disco quando maior que uma linha, respeitar a ordem de flags específica de cada CLI, fixar o slug de modelo, proibir explicitamente no prompt que o revisor invoque outro binário de CLI ou execute scripts do repositório por conta própria (gotchas.md 2026-09-17: um `codex exec` como implementer abriu sozinho um `opencode run` no mesmo checkout; 2026-09-20: um `opencode run` com brief somente-leitura executou um script de build e reconstruiu `dist/`) — a única execução permitida ao revisor são os comandos de verificação declarados em `.harness/project.yaml` (`commands.test` e `commands.lint`; por exemplo `make test`) — nunca `commands.build`, que pode regravar artefatos versionados como `dist/` e cair na reversão de RF-10 —, para obter o resultado da suíte (decisão do dono, 2026-09-21), e distinguir falha de transporte (exit não-zero, timeout, saída sem o bloco de veredito esperado) de um veredito real. A skill é portável: nenhum caminho absoluto, token ou binário desta máquina em seu texto.
- RF-02 Arquivo local `.harness/local.yaml` guardando o que é específico desta máquina: o caminho de cada binário de CLI quando não está no PATH — sempre relativo ao home (`~/.grok/bin/grok`, `~/.opencode/bin/opencode`) ou ao projeto, nunca absoluto com o diretório home expandido (nome do usuário embutido), para que o mesmo arquivo funcione em qualquer máquina (decisão do dono, 2026-09-21) — e a lista de slugs de modelo medidos localmente para cada CLI — nunca credencial ou token. O arquivo é gravado em `.harness/` esteja a pasta ignorada pelo git ou não (decisão do dono, 2026-09-21): ele não contém segredo, e um caminho de outra máquina apenas degrada o revisor para not-run (RF-07). Antes da primeira gravação o Coordenador roda `git check-ignore .harness/local.yaml`; se o caminho não estiver ignorado, avisa o dono uma vez e registra o aviso em `.harness/MEMORY.md`, sem editar o `.gitignore` sozinho (`/dev-harness:setup` só escreve `.harness/project.yaml` e os registros ausentes de `.harness/`, por `.commands/setup.md`). Premissa: alguns projetos consumidores versionam `.harness/` e outros o ignoram por inteiro (como este próprio repositório). A skill e os papéis do kit leem `.harness/local.yaml` em vez de terem esses valores embutidos.
- RF-03 Novo campo opcional `reviewers:` em `.harness/project.yaml` (decisão do dono, 2026-09-21; ver seção 8) declarando, por etapa de revisão do kit (`document`, `code`, `security` — `verify` fica fora da v1, candidata a versão futura), a lista de revisores. Sem o campo, o fluxo atual continua: só agentes Claude, como hoje. Com o campo, o Coordenador invoca os revisores listados. Cada entrada da lista é `claude` (usa o agente do kit com o modelo já definido em `.agents/<role>.md`) ou `cli:<binário>/<slug>` (usa uma CLI externa configurada em `.harness/local.yaml`). O modo é sempre paralelo quando a etapa lista mais de um revisor — não há modo sequencial em v1; quando a lista tiver mais revisores do que o teto de concorrência vigente, ou quando a nota da CLI na skill proibir execuções simultâneas (por exemplo `opencode`), o Coordenador executa em levas — "paralelo" significa tão paralelo quanto o teto e as CLIs permitem.
- RF-04 Quando um revisor for `cli:<binário>/<slug>`, o Coordenador monta o prompt dessa chamada a partir do corpo de `.agents/<role>.md` (sem o frontmatter YAML) mais o texto da skill de revisão referenciada (`code-review`, `document-review` ou `security-review`) mais o pacote de contexto do despacho (escopo, diff, fonte). Não existe um prompt separado mantido à mão para a CLI; ele é montado em tempo de despacho a partir dos mesmos arquivos que um agente Claude usaria, o que impede o prompt da CLI divergir do prompt do agente com o tempo.
- RF-05 O Coordenador mescla N vereditos da mesma etapa: qualquer achado bloqueador de qualquer revisor (Critical/Major em `code-review`, gap/conflito/critério fraco em `document-review`, vulnerabilidade demonstrada/exposição confirmada em `security-review`) torna o veredito mesclado bloqueador, mesmo que os demais revisores tenham aprovado. Achados equivalentes de revisores diferentes (mesmo arquivo e linha, ou mesma seção do documento) são deduplicados no relatório mesclado com a lista de quem os reportou. Quando revisores divergem sobre o mesmo ponto sem que um deles aponte um bloqueador claro, o relatório mescla registra a divergência e apresenta os dois vereditos ao dono; o Coordenador não escolhe um autonomamente.
- RF-06 O registro persistente varia por etapa, seguindo o que o kit já grava: para `document`, é `<document>.review.md`; para `code` e `security`, é a entrada de achados que o Coordenador grava em `.harness/MEMORY.md` (e em `.harness/RISKS.md` para exposição confirmada), como `.commands/review.md` e `.commands/secure.md` já mandam. Em todos os casos, cada achado leva a tag do revisor que o produziu (`claude` ou `cli:<binário>/<slug>`), preservando o formato de severidade/localização/cenário já definido nas skills de revisão existentes.
- RF-07 Quando um binário de CLI configurado em `reviewers:` de `.harness/project.yaml` não existe nesta máquina (ausente em `.harness/local.yaml` e fora do PATH), o Coordenador registra esse revisor como not-run com o motivo ("binário ausente nesta máquina") no relatório da etapa e segue com os revisores restantes configurados para a etapa. Se todos os revisores de uma etapa ficarem not-run, a etapa inteira é reportada not-run — nunca aprovada por omissão.
- RF-08 O sinal de veredito observável é definido por etapa: em `document`, a linha `approved` ou `changes required` sob `## Verdict`; em `code`, a linha `Review status:` sob `## Verdict`; em `security`, a seção `## Findings` com ao menos uma entrada `### <SEVERITY>` ou a linha literal "No demonstrated vulnerability or confirmed exposure found". Quando uma chamada de CLI devolve exit 0 sem esse sinal, ou estoura o timeout do revisor (campo opcional por revisor em `reviewers:` de `.harness/project.yaml`, padrão 15 minutos), o Coordenador trata isso como falha de transporte daquele revisor nesta rodada: não conta como uma rodada de correção gasta e não é relatada como um veredito de aprovação ou reprovação. É registrada como not-run com o motivo da falha de transporte.
- RF-09 Casos de eval sob `evals/cases/`: revisão paralela Claude+CLI numa etapa configurada, revisão só-CLI (dois revisores CLI, nenhum Claude), binário ausente, mescla com um achado bloqueador vindo só da CLI, e atribuição correta do achado ao revisor no relatório.
- RF-10 Toda invocação de CLI como revisor usa o modo somente-leitura do binário quando ele existe (por exemplo `codex exec -s read-only`, `mcode --permission off`), documentado por CLI na skill `external-clis`. Depois de cada chamada, o Coordenador confere `git status` contra o estado congelado antes da revisão; qualquer alteração no workspace feita pelo revisor CLI é falha de transporte (RF-08): o veredito é descartado, a alteração é revertida e o revisor fica not-run com o motivo.

**Não entra**
- Construtores (builders) via CLI externa. Só papéis de revisão (`document-validator`, `code-reviewer`, `security-reviewer`) ganham a opção de CLI nesta v1; `backend-builder`, `frontend-builder` etc. continuam só Claude.
- CLIs de mídia (`mmx`): não são revisores, ficam fora por definição.
- Uso interativo/TUI de qualquer CLI a partir do Coordenador. Toda chamada é headless, como já regrado em `fleet-clis` hard rule 2.
- Instalar, autenticar ou atualizar qualquer CLI. A skill só invoca o que já está instalado; binário ausente é not-run, nunca uma instalação automática.
- Cadeia de fallback automática entre CLIs diferentes dentro da mesma etapa (por exemplo, se `codex` falhar, tentar `grok` sozinho sem isso estar na lista configurada). Um revisor que falha fica not-run; o dono decide se quer configurar um substituto na lista.

## 5. Critérios de aceite

- AC-01 (RF-03) Quando o dono configurar a etapa `code` no campo `reviewers:` de `.harness/project.yaml` com `[claude, "cli:codex/gpt-5.6-sol"]`, então o Coordenador despacha `code-reviewer` (Claude) e a chamada à CLI `codex` em paralelo, e aguarda os dois antes de produzir o relatório mesclado.
- AC-02 (RF-03) Quando uma etapa listar só revisores `cli:...` e nenhum `claude`, então nenhum agente Claude é despachado para essa etapa e o relatório mesclado é produzido só a partir dos vereditos das CLIs.
- AC-03 (RF-07) Quando um revisor `cli:<binário>/<slug>` configurado não tiver o binário resolvível nesta máquina (nem no PATH, nem em `.harness/local.yaml`), então esse revisor aparece no relatório como not-run com o motivo, e a etapa segue com os revisores restantes.
- AC-04 (RF-07) Quando todos os revisores configurados para uma etapa ficarem not-run (nenhuma CLI resolvível e nenhum `claude` na lista), então a etapa inteira é reportada not-run, nunca como aprovada.
- AC-05 (RF-08) Quando uma chamada de CLI devolver exit 0 sem o sinal de veredito da etapa (linha `approved`/`changes required` sob `## Verdict` em `document`; linha `Review status:` sob `## Verdict` em `code`; seção `## Findings` com entrada `### <SEVERITY>` ou a linha "No demonstrated vulnerability or confirmed exposure found" em `security`), ou estourar o timeout do revisor, então o Coordenador registra esse revisor como not-run por falha de transporte, não consome uma rodada de correção, e não trata a ausência de veredito como aprovação.
- AC-06 (RF-05) Quando qualquer revisor de uma etapa (Claude ou CLI) reportar um achado bloqueador — Critical/Major em `code`, gap/conflito/critério fraco em `document`, vulnerabilidade demonstrada ou exposição confirmada em `security` —, então o veredito mesclado da etapa é bloqueador (`request changes`/`changes required`/`blocking`, conforme a etapa) mesmo que os demais revisores tenham aprovado sem achados.
- AC-07 (RF-05) Quando dois revisores devolverem avaliações diferentes sobre o mesmo ponto sem que nenhum deles aponte um bloqueador claro, então o relatório mesclado registra a divergência com os dois vereditos citados, e o Coordenador não resolve a divergência sozinho.
- AC-08 (RF-04) Quando um revisor `cli:<binário>/<slug>` for despachado para a etapa `code`, então o texto enviado como prompt contém o corpo de `.agents/code-reviewer.md` (sem o frontmatter) e o texto da skill `code-review`, montados no momento do despacho — nunca um arquivo de prompt separado mantido à parte para a CLI.
- AC-09 (RF-06) Quando o Coordenador gravar o registro persistente de uma etapa com revisores mistos — `<document>.review.md` em `document`, ou a entrada de achados em `.harness/MEMORY.md`/`.harness/RISKS.md` em `code`/`security` —, então cada achado nesse registro está anotado com o revisor que o produziu (`claude` ou `cli:<binário>/<slug>`).
- AC-10 (RF-01, RF-02) Quando o repositório do kit for inspecionado após a mudança, então nenhum caminho absoluto com home expandido, token ou slug de modelo medido nesta máquina aparece em `.skills/external-clis/`, `.agents/`, `.commands/` ou `templates/`; esses dados só existem em `.harness/local.yaml`, e mesmo lá os caminhos são relativos ao home (`~/...`) ou ao projeto.
- AC-11 (RF-09) Quando os casos de eval propostos (`evals/cases/external-clis-*.md`) forem executados, então cada um cobre exatamente o cenário do seu nome (paralelo Claude+CLI, só-CLI, binário ausente, mescla com bloqueador vindo só da CLI, atribuição no relatório) sem depender de uma CLI de fato instalada na máquina de CI (usam duplo/mock do transporte).
- AC-12 (RF-10) Quando um revisor CLI alterar qualquer arquivo do workspace durante a revisão, então seu veredito é descartado, a alteração é revertida, o revisor aparece como not-run por falha de transporte, e o relatório mesclado não usa seus achados.
- AC-13 (RF-05) Quando dois revisores reportarem o mesmo achado (mesmo arquivo e linha, ou mesma seção do documento), então o relatório mesclado o lista uma vez com os dois revisores anotados.
- AC-14 (RF-02) Quando `.harness/local.yaml` não estiver ignorado pelo git do projeto consumidor, então o Coordenador avisa o dono antes da primeira gravação, registra o aviso em `.harness/MEMORY.md`, grava o arquivo mesmo assim e não edita o `.gitignore`.
- AC-15 (RF-01) Quando o prompt de um revisor CLI for montado, então ele proíbe invocar outro binário de CLI e executar scripts do repositório, e permite apenas os comandos de verificação declarados em `.harness/project.yaml`.

## 6. Restrições e impacto técnico

- Dados: novo campo opcional `reviewers:` em `.harness/project.yaml` (sem segredos; `/dev-harness:setup` continua não reescrevendo o arquivo — o dono acrescenta o campo à mão ou por um comando futuro) e novo arquivo `.harness/local.yaml` (nunca contém segredo ou token; gravado mesmo que `.harness/` não esteja ignorado; o Coordenador confere `git check-ignore .harness/local.yaml` antes da primeira gravação e avisa o dono uma vez se o caminho não estiver ignorado, sem alterar o `.gitignore` sozinho — `/dev-harness:setup` não escreve fora de `.harness/project.yaml` e dos registros ausentes de `.harness/`). Nenhuma migração de dado existente.
- Contratos: os formatos de saída de `code-review`, `document-review` e `security-review` (`.skills/*/SKILL.md`) ganham um campo de atribuição de revisor por achado; nenhuma seção nova é adicionada a essas skills. O sinal de veredito observável que RF-08 usa para distinguir falha de transporte de veredito real já existe em cada formato hoje: `document` (linha sob `## Verdict`), `code` (linha `Review status:` sob `## Verdict`), `security` (entrada `### <SEVERITY>` ou a linha literal de ausência de achado sob `## Findings`) — só leitura desse sinal já existente, sem mudar a estrutura. `.commands/review.md`, `.commands/discover.md` e `.commands/secure.md` passam a citar a skill `external-clis` e a leitura do campo `reviewers:` de `.harness/project.yaml` na seção de Routing; `.commands/secure.md` e `.agents/coordinator.md` passam a dizer que uma lista em `reviewers:` de `.harness/project.yaml` é autorização explícita do dono para o provedor e o modelo daquela etapa, cobrindo as regras já existentes de não rebaixar a revisão de segurança do padrão Opus e de não introduzir provedor pago sem autorização.
- Segurança: `.harness/local.yaml` pode conter caminhos de binário e slugs, nunca segredos de autenticação — a autenticação de cada CLI já vive fora do repositório (por exemplo `~/.grok/`, `~/.opencode/`, `~/.minimax/`), como hoje. A skill nunca lê nem imprime essas credenciais. Toda invocação de CLI como revisor usa o modo somente-leitura do binário (RF-10); qualquer alteração no workspace detectada depois da chamada descarta o veredito e marca o revisor not-run.
- Operação: nenhuma CLI é instalada, autenticada ou atualizada pelo kit; a skill só invoca o que já está no PATH ou no caminho declarado em `.harness/local.yaml`.
- Stack e dependências: nenhuma dependência nova de build. Chamadas a CLI são feitas via shell pelo Coordenador (Bash), como a skill pessoal já faz — ver decisão pendente sobre um subcomando `dh` para essa orquestração.
- Eval: `evals/cases/external-clis-parallel.md` (Claude+CLI em paralelo), `evals/cases/external-clis-only.md` (dois revisores CLI, nenhum Claude), `evals/cases/external-clis-missing-binary.md` (binário ausente degrada sem bloquear a etapa), `evals/cases/external-clis-merge-blocker.md` (achado bloqueador vindo só da CLI vira veredito bloqueador), `evals/cases/external-clis-attribution.md` (atribuição do achado ao revisor no relatório persistente).

## 7. Alternativas descartadas

| Alternativa | Por que não |
|---|---|
| Manter `fleet-clis` como skill pessoal fora do kit, sem integração | É o estado atual; não resolve o pedido do dono de configurar revisores por etapa em `.harness/` nem reaproveitar o prompt dos agentes do kit |
| Reescrever o prompt de cada revisor especificamente para cada CLI, mantido à mão | Gera deriva entre o prompt do agente Claude e o prompt da CLI ao longo do tempo (risco já citado pelo dono); RF-04 evita isso montando o prompt da CLI a partir dos mesmos arquivos-fonte |
| CLI externa também como builder, não só revisor, já nesta v1 | Amplia muito o raio de risco (uma CLI externa editando o workspace sem o mesmo controle de write-set dos builders do kit); fora do pedido original do dono, que falou só em "verificação em pares" |
| Cadeia de fallback automática entre CLIs (se uma falhar, tentar outra sem estar configurada) | Esconde do dono qual revisor de fato rodou; contradiz a regra de nunca degradar silenciosamente (RF-07); o dono configura explicitamente os revisores que quer |

## 8. Riscos e decisões pendentes

- Risco: saída de CLI não segue o formato de veredito esperado (frequente no histórico de `gotchas.md` da skill pessoal: 45 ocorrências entre 2026-08-18 e 2026-09-20, incluindo exit 0 sem veredito, timeout sem saída, e um caso real de CLI invocando outra por conta própria no mesmo checkout em 2026-09-17) · mitigação: RF-01 proíbe explicitamente no prompt que o revisor invoque outro binário; RF-08 trata qualquer saída fora do sinal esperado como falha de transporte, nunca como veredito, sem consumir rodada de correção; RF-10 confere `git status` contra o estado congelado depois de cada chamada e reverte qualquer alteração.
- Risco: custo de rodar múltiplas CLIs pagas por revisão · mitigação: `reviewers:` é opt-in por etapa; o padrão sem esse campo continua sendo só Claude, como hoje.
- Risco: execuções simultâneas demais sobrecarregam a máquina ou travam a CLI (gotchas.md 2026-08-31: dois `opencode run` ao mesmo tempo deram "database is locked"; 2026-09-08: "nunca lançar dois CLIs pesados em paralelo" sob pressão de memória) · mitigação: RF-03 executa em levas quando a lista excede o teto de concorrência vigente ou a CLI não aceita execuções simultâneas.
- Risco: segredo ou token de uma CLI vazando para dentro do repositório versionado · mitigação: `.harness/local.yaml` guarda só caminho de binário e slug de modelo, nunca credencial; autenticação de cada CLI já vive fora do repo hoje (fato observado em `fleet-clis`), e a skill não lê nem imprime esses arquivos de auth.
- Risco: deriva entre o prompt de um agente do kit e o texto que a CLI de fato recebe, se alguém copiar o prompt manualmente para outro lugar · mitigação: RF-04 monta o prompt da CLI a partir de `.agents/<role>.md` e da skill em tempo de despacho; nenhuma cópia mantida à parte.
- Decisão fechada (dono, 2026-09-21): a configuração por etapa é o campo `reviewers:` em `.harness/project.yaml`, não um arquivo irmão. Sem o campo, o fluxo padrão de hoje (só Claude); com o campo, o Coordenador invoca os revisores listados. `/dev-harness:setup` escreve `project.yaml` uma única vez e não o reescreve (`.commands/setup.md`), então o campo sobrevive.
- Decisão fechada (dono, 2026-09-21): v1 só com a skill `external-clis` em prosa (Bash direto pelo Coordenador), sem subcomando `dh`. Razões mantidas: `cmd/dh` não orquestra processos externos nem faz parsing de saída de LLM hoje; `fleet-clis` + `gotchas.md` mostram que o valor está na prosa versionada; um subcomando fica mais barato depois de saber que problema resolve. Revisitar em 2026-10-21 (30 dias) com evidência de uso: se o parsing de veredito quebrar ou os retries manuais se repetirem, promover para `dh review run <etapa>`.
- Decisão fechada (dono, 2026-09-21): revisores CLI contam contra o mesmo teto de "no máximo dois especialistas concorrentes" de `.agents/coordinator.md`; cada revisor, Claude ou CLI, é um especialista concorrente para efeito desse limite.
- Decisão fechada (dono, 2026-09-21): a etapa `verify` (`qa-verifier`) fica fora da v1; candidata a uma versão futura, quando o contrato de revisor somente-leitura para QA for definido.
