dev-harness tutorial

From install to release: how to use the kit day to day, what it writes to .harness/, and what each command does.

date 2026-09-30 status internal path docs/en/tutorial.html

01Install

Prerequisites: Git and an authenticated Claude Code with access to a model. The package ships the dh binary; no interpreter is needed. Go 1.22+ only for people who maintain the kit.

  1. From the marketplace. Inside a Claude Code session, in the project you will work on. The URL form downloads only marketplace.json, without cloning the repository: 
    /plugin marketplace add https://raw.githubusercontent.com/danielmalka/dev-harness/main/.claude-plugin/marketplace.json
/plugin install dh@dev-harness
    The short form /plugin marketplace add danielmalka/dev-harness also works, but it clones the whole repository (about 90 MB, because of the dh binaries of every version) and failed once with fetch-pack: invalid index-pack output (not reproduced). With a local clone, /plugin marketplace add /path/to/clone works too. In every form, install downloads only the plugin folder, at the tag pinned in .claude-plugin/marketplace.json, which sets the version. For a team, the project can declare the marketplace under extraKnownMarketplaces and the plugin under enabledPlugins in .claude/settings.json.
  2. Or from the clone (development). Clone the repository and load the generated package, in the target project: 
    claude --plugin-dir "/absolute/path/to/clone/dist/claude-code/dev-harness" --agent coordinator
    Inside quotes ~ does not expand: "~/projects/..." does not exist, Claude silently ignores the plugin and --agent coordinator fails with "not found". Use $HOME/... or the full path. If the runtime needs the qualified name, use --agent dh:coordinator.
  3. Migrating from before 0.8.0. /plugin uninstall dev-harness@dev-harness, then /plugin install dh@dev-harness; replace /dev-harness: with /dh: in your own scripts and notes.
  4. Deactivate. End the session without --plugin-dir, or uninstall the plugin. The .harness/ files in your project stay: the kit never deletes your work.

The package includes settings.json and hooks/hooks.json, which write per-session snapshots to ~/.claude/dev-harness/sessions/<session_id>.json, local files only, pruned after 7 days.

02Local dashboard

A local page shows projects in progress, open PRDs, and Claude Code sessions with their state (working, idle, waiting, error, ready, attention). To run:

  1. /dashboard inside a Claude Code session. The command (registered by the mod, not a traditional /dh:) starts a server on the default port 4747 at http://127.0.0.1:4747 and prints the URL. It accepts arguments:
    • --port N to change the port (e.g. /dashboard --port 4748). If the port is busy, the command warns clearly.
    • --detach to run detached; by default the server runs while the session is active.
    • --stale D and --done-decay D for display tuning (sensible defaults come pre-configured).
  2. Configure projects. The DH_DASHBOARD_ROOTS variable points to folders that contain projects. Projects are direct subfolders that have a .harness/. Multiple paths separate by ;: 
    export DH_DASHBOARD_ROOTS="/home/you/work;/home/you/side-projects"
  3. Custom avatars (optional). DH_DASHBOARD_SPRITES points to a folder of icons in jevmon format: one file per pose (<pose>.png or frames <pose>_01.png, <pose>_02.png, etc.), plus an optional poses.json that maps states. The kit ships 6 example icons (idle, working, waiting, error, ready, attention). When a pose does not exist in your owner folder, the dashboard falls back to the kit default. The server never serves an icon with a free path (without a known pose name) for safety.

03VS Code extension

The dev-harness-vscode extension brings the local dashboard into VS Code, shows session state in the status bar, and opens a terminal to run a dh command without leaving the editor.

  1. Install the extension. Download dev-harness-<version>.vsix from release latest of the danielmalka/dev-harness-vscode repository. In VS Code, open the command palette (Ctrl+Shift+P / Cmd+Shift+P), search for "Extensions: Install from VSIX..." and select the file.
  2. Configure the dashboard. Three optional settings in VS Code Settings (Ctrl+,):
    • dh.dashboard.port: server port (default 4747).
    • dh.dashboard.roots: list of root folders that contain kit projects (e.g., ["/home/you/work", "/home/you/side-projects"]).
    • dh.dashboard.sprites: folder of custom icons (jevmon format, same as dashboard).
  3. Open the dashboard. In the activity bar (left side), click the "Dev Harness" icon to open the view. If the server is not running, click "Start dashboard" to bring it up in detached mode. The dashboard loads in an iframe.
  4. Open a session. Open the command palette and search for "dh: open session". Choose the project folder (subfolders under roots, or open workspace folders) and a /dh:<name> command from the 19 (e.g., /dh:auto or /dh:improve). An integrated terminal will open in that folder, run claude and type the command — you press Enter to submit.

04First session

Open Claude Code in the project with the Coordinator as main agent (--agent coordinator when loading from the clone), and run:

  1. /dh:doctor diagnoses kit, runtime and project. It writes nothing. Without Claude, from the clone: dist/claude-code/dev-harness/bin/dh doctor dist/claude-code/dev-harness.
  2. /dh:setup reads the project (stack, manifests, test, lint and build commands) and proposes the profile. With permission to write, it records .harness/project.yaml and, only when they do not exist yet, MEMORY.md, EPOCHAL.md and RISKS.md. The language field (en by default, pt-br if you wrote in Portuguese) picks templates/<lang>/. A project AGENTS.md is canonical; a CLAUDE.md is read too, and on conflict AGENTS.md wins.
  3. Optional practice. The evals/fixtures/slice-01 fixture (in the kit clone; Python 3, unittest, one criterion red on purpose) is there for a first plan, build, verify, review, handoff cycle. Do not copy expected/greet.py over the code.

05What lives in .harness/

PathWhat it is for

local.yamlCLI paths and slugs for this machine. No secrets.

EPOCHAL.mdArchive of memory batches, written by /dh:consolidate-memory. Read only for a concrete historical question.
RISKS.mdSevere incidents, with cause, resolution and prevention.

Only the Coordinator writes MEMORY.md, EPOCHAL.md and RISKS.md. Other agents return proposals. The Claude Code plugin enforces this rule at runtime: a subagent that tries to write those files is blocked. The disk is the truth: if you deleted records, the Coordinator does not recreate them from what it remembers of the conversation.

06Flows

The kit has 13 agents and 19 commands. You talk to the Coordinator; it dispatches the specialists and holds the authorization: nothing is installed, committed, published or deployed without you authorizing it.

Feature, from ask to release

  1. /dh:discover <idea>. product-discovery asks one blocking question at a time and writes the PRD (Problema, Solução, Regras, Docs). A document-validator reviews it for up to 2 rounds; you get the PRD after approved or the cap.
  2. /dh:plan. implementation-planner slices the work into PLAN.md and one TASK.md per slice, each with its lane (backend, frontend, dados, infra or a test lane). The validator reviews the plan.
  3. /dh:build <ticket>. builder implements the slice in the ticket's lane, qa-verifier writes and runs tests on the frozen state, and a reviewer reviews. Up to 6 correction rounds; any edit invalidates the evidence and the review. Repeat per ticket. If the change touches authentication, data, input or execution, run /dh:secure.
  4. /dh:review feature PRD-<n> and /dh:verify. The final review looks at the seams between tickets against the whole PRD, with QA using the screen as a client (Playwright headless) when there is one. Outcome: FEATURE APROVADA, REPROVADA or BLOQUEADA. /dh:verify widens the acceptance matrix at any point.
  5. /dh:document. docs-guide updates what the change requires. Documentation ships in the same PR, never in a PR of its own.
  6. /dh:release. release-manager assembles the readiness package (version, notes, compatibility, rollout, rollback). It stops at "ready for decision": commit, push, tag and deploy only with your authorization.

Verification default: deterministic checks (dh validate, build, tests) plus 1 reviewer on the first pass (claude when reviewers.code lists it; with the field absent, Claude only). A re-entry of the same task advances one entry. The full code list joins only when you ask. The security stage dispatches its full list in /dh:secure and does not widen the code review. Detail is in docs/adr/ADR-004-duvida-e-rotacao.md.

All at once: /dh:auto

/dh:auto takes an idea, an approved PRD or an approved PLAN.md, detects the start stage and asks one 7-item questionnaire: start stage, decision mode (a: decide and record everything; b: ask only product or contract decisions, the default; c: ask everything), commit and push, PR, merge, tag, and an eval spend cap (zero or absent means no paid evals). Then it chains discover, plan and build on a single branch, with secure per slice when it applies, review at the end and release. It stops outright on a demonstrated vulnerability, a destructive action, an unauthorized install, the spend cap or the round cap. State lives in .harness/tasks/AUTO-<n>/BRIEF.md; /dh:resume continues where it stopped.

Bug: /dh:fix

Give the literal error or the reproduction steps. debugger reproduces, isolates the cause (marked fact or hypothesis) and, if you authorized file changes, applies the smallest fix at the origin of the bad value, with a regression test seen failing before and passing after. Then qa-verifier and a reviewer run. With no reproduction the result is "inconclusive", never a presumed fix.

Refactor: /dh:refactor

Needs a named structural problem and the baseline of the checks before anything moves. builder (mode refactor) works in small, revertible steps; any observable difference is a defect. A new feature goes to /dh:plan.

Verification: /dh:verify

Given acceptance criteria and a stable change, qa-verifier returns a pass, fail or not-run matrix and, for a user interface, checks keyboard use, two viewport widths and loading, error and empty states, with captures under .harness/tasks/<id>/evidence/.

Long session: handoff, resume, consolidate-memory

  1. /dh:handoff records objective, constraints, files, decisions, evidence and the next step under .harness/tasks/<id>/. With no objective it stops and asks.
  2. /dh:resume in the next session reconciles the record with the tree (repo-scout checks the files) and continues only what is already authorized. Where the two disagree, the tree wins.
  3. /dh:consolidate-memory archives MEMORY.md into EPOCHAL.md, verifies the copy and only then shortens the memory. It asks you to confirm that no other session is writing.

Kit care: /dh:improve

For a concrete case where the kit misbehaved (prompt, expected, observed). harness-maintainer names the owning asset, makes the smallest edit in the sources (.agents/, .skills/, .commands/, templates/, profiles/; never dist/) and measures before and after with a paid eval (running /dh:improve counts as your request for it). Afterwards, /dh:doctor.

Understand before changing: /dh:understand

Ask in terms of behavior ("where does password reset go through?"). repo-scout returns entries, dependencies and flow, read-only.

07Configuration

.harness/project.yaml

Written by /dh:setup and editable by hand. No secrets or absolute paths. Fields:

  • language: en or pt-br. Picks templates/<lang>/ for records and artifacts and the language of the Coordinator's replies. Dispatches, code and commits are always in English.
  • commands: test, lint, build, run, each with a value and a source; null means "do not guess". With no discoverable command, the check is reported not-run.
  • reviewers: optional, per stage (document, code, security; verify is out). Each entry is claude, "cli:<binary>/<slug>" (15-minute default timeout) or {reviewer: "cli:<binary>/<slug>", timeout_minutes: <n>}. Absent, the flow is Claude-only.
language: en
commands:
  test:
    value: go test ./...
    source: observed ci.yml
reviewers:
  document: [claude, "cli:codex/<slug>"]
  code: [claude]
  security: [claude]

.harness/local.yaml

Machine data: under binaries, where to find each CLI that is not on PATH; under models, the measured slugs. Paths are always home-relative (~/.grok/bin/grok) or project-relative, never the expanded home, so the same file works on any machine. A binary that does not resolve leaves the reviewer not-run, with the reason. File model: .skills/external-clis/references/local.yaml.example (in the clone).

08Advanced

Looped planning: /dh:plan-loop

For a new feature, instead of a single plan: the implementation-planner (Claude) competes with an external CLI planner in waves. Rotation follows the order of reviewers.document; each candidate is judged by the full reviewer list, and the loop converges when all approve with no blocking finding, with at least one reviewer that is not Claude and did not write the candidate. Caps are plan_loop.wave_cap (default 6) and plan_loop.dispatch_cap (default 48) in project.yaml. With no eligible CLI it falls back to /dh:plan. Delivering the plan does not authorize building.

External CLI reviewers and clone isolation

Listed under reviewers, they run beside Claude or in its place. The binary is resolved from PATH and, failing that, from local.yaml; a reply only counts with the stage's verdict signal. A binary with a documented, measured read-only mode (today codex) uses its own sandbox. One without such a mode (grok, opencode, mcode, claude as a CLI) runs in a disposable clone, and agy as a reviewer runs on the live tree with a freeze comparison. The clone is not a sandbox: writes outside it are detected on the live tree, never prevented, and writes outside the project are not detected. Any detected change discards the verdict. A grok may need an explicit Bash permission rule in .claude/settings.local.json before the Coordinator can dispatch it. Per-binary details: the external-clis skill.

Evals on request only

Paid eval measurement is not part of the normal flow. It only runs when you ask: directly, inside /dh:improve, or through the spend cap in the /dh:auto questionnaire. When it runs, it is the minimum the change requires, one run by default.
